En ServiClient: En varias operaciones se emplea el identificador empresaId y búsquedas filtradas por empresa.

Eje 1 · Estructuras y patrones

Arquitectura que realmente usamos

No recites definiciones extensas: abre los archivos en el orden de una petición real y explica una responsabilidad por archivo.

Entiende la teoría antes de mostrar la implementación

Teoría básica: MVC, DAO, SOLID y TDD

Recuerda el significado de cada concepto y conéctalo con una clase real. No hace falta explicar todo el archivo: muestra la anotación, dependencia o método relevante.

MVC: Modelo – Vista – Controlador

Modelo: datos que maneja el sistema; Vista: lo que ve la persona; Controlador: recibe una petición y decide qué acción atender. En Spring Boot hay además una capa Service para la lógica de negocio.

En ServiClient: ClienteController recibe GET /clientes, pide datos a clienteService.listarClientes(...) y devuelve "clientes/index" para que Thymeleaf genere HTML (SSR).

DAO y Repository

El patrón DAO aísla el acceso a datos. Con Spring Data JPA, las interfaces Repository cumplen esa función y heredan operaciones básicas sin escribir SQL en cada caso.

En ServiClient: ClienteRepository extends JpaRepository<Cliente, Long>. El método findByIdAndEmpresaId(...) muestra una consulta ligada a la empresa.

SOLID: SRP y DIP

SRP busca que una clase tenga una sola razón de cambio. DIP busca depender de abstracciones, no de implementaciones concretas. Las capas favorecen SRP, pero no demuestran que toda clase lo cumpla perfectamente.

En ServiClient: ClienteController declara private final IClienteService clienteService y ClienteService implements IClienteService: ejemplo claro de DIP.

TDD y pruebas automatizadas

JUnit ejecuta pruebas y Mockito simula dependencias. TDD es una forma de desarrollar: primero una prueba falla (RED), luego pasa (GREEN) y después se mejora el código (REFACTOR). Tener pruebas no prueba por sí solo que se trabajó con TDD.

En ServiClient: TicketServiceTest tiene @Test, assertEquals y verify para comprobar la creación de un ticket.

SSR: renderizado del servidor

El servidor genera el documento HTML antes de enviarlo al navegador. No significa que la web no pueda usar JavaScript: solo describe dónde se construye inicialmente la página.

En ServiClient: Thymeleaf toma la plantilla templates/clientes/index.html y los atributos que envía el controlador.

Seguridad: autenticación vs autorización

Autenticación: verificar quién inicia sesión. Autorización: decidir qué recursos puede utilizar. BCrypt guarda un hash de contraseña; CSRF ayuda a proteger peticiones con sesión; el aislamiento multiempresa restringe acceso entre organizaciones.

En ServiClient: SecurityConfig define BCryptPasswordEncoder, SecurityFilterChain y reglas hasRole.

Idea para explicarlo en voz alta: “El controlador recibe la petición, el servicio atiende la operación, el repositorio accede a MySQL y Thymeleaf presenta la vista. Las interfaces desacoplan el controlador; las pruebas y Spring Security ayudan a verificar y proteger las funciones.”
Precaución para la sustentación: No afirmes que el proyecto cumple los cinco SOLID ni que todas sus rutas son seguras. En la versión dev revisada, el patrón /portalusuario/** estaba en permitAll(); conviene revisar la rama integrada antes de hacer afirmaciones sobre el portal.
Ejemplo explicado: ¿qué ocurre al abrir «Clientes»?
  1. El navegador solicita GET /clientes.
  2. ClienteController recibe la solicitud y obtiene el empresaId del usuario autenticado.
  3. El controlador llama a la interfaz IClienteService; ClienteService procesa la solicitud.
  4. ClienteRepository consulta registros con Spring Data JPA e Hibernate.
  5. El controlador envía datos al modelo de la vista y retorna clientes/index.
  6. Thymeleaf genera el HTML visible en el navegador.

Mapa de MVC + servicio + DAO

GET /clientes→ClienteController→IClienteService→ClienteService→ClienteRepository→MySQL

Vista: src/main/resources/templates/clientes/index.html. El controlador devuelve "clientes/index" para que Thymeleaf construya la respuesta HTML.

MVCSolicitud HTTP → datos/modelo → vista web.
DAORepositorio JPA aísla las operaciones de acceso a datos.
SOLIDSRP favorecido por responsabilidades y DIP por interfaces.

La diferencia entre SRP, DIP y TDD

SRP Separar responsabilidades: controlador HTTP, servicio de negocio, repositorio de datos. No asegura que todas las clases cumplan SRP perfectamente.

DIP ClienteController recibe IClienteService; ClienteService implementa esa interfaz. Esta es la evidencia fuerte.

Pruebas/TDD JUnit y Mockito verifican escenarios; para decir TDD debes enseñar un test que falló (RED), la corrección (GREEN) y refactorización sin romperlo (REFACTOR).

Para enseñar seguridad abre SecurityConfig.java y localiza BCryptPasswordEncoder y hasRole("ADMIN"). La separación multiempresa también aparece en findByIdAndEmpresaId del repositorio.
Eje 2 · Recursos Java y seguridad

Qué librería, para qué y dónde

En la clase de la semana 10 se explican beneficios como reutilización de código, productividad, mantenibilidad y menos trabajo repetitivo. Relaciona cada beneficio con una implementación.

Entiende la teoría antes de mostrar la implementación

Teoría: ¿qué es una librería y qué beneficio aporta?

Una librería reúne funcionalidades reutilizables; así evitamos programar desde cero tareas comunes. En clase se resaltaron reutilización, productividad, calidad y facilidad de mantenimiento.

Google Guava · validación

Proporciona utilidades de Java como Preconditions, que comprueban condiciones y permiten fallar pronto con mensajes claros. Su ventaja no es eliminar toda validación, sino hacerla más legible.

En ServiClient: EmpresaService.registrarEmpresaCompleta() usa checkNotNull y checkArgument para datos obligatorios.

Apache POI · archivos Office

Permite leer y generar archivos Microsoft Office. Con XSSFWorkbook se crean archivos Excel .xlsx, sus hojas, filas y celdas. Beneficio: exportar información sin construir el formato manualmente.

En ServiClient: ClienteService.exportarClientesExcel() crea el libro, la hoja “Clientes” y escribe las columnas.

Apache Commons Lang · texto

Amplía las utilidades para trabajar con cadenas, objetos y números. StringUtils.isAnyBlank() detecta campos vacíos o solo espacios; equals() compara textos.

En ServiClient: PortalUsuarioController usa StringUtils durante el cambio de contraseña en la rama feature/portal-usuario.

Logback y SLF4J · registros

SLF4J es la interfaz para escribir mensajes y Logback es una implementación de registro. info señala un evento normal, warn una advertencia y error un fallo.

En ServiClient: TicketService registra log.info al crear un ticket y log.warn cuando la prioridad es crítica.

Spring Security · protección

Es un framework de seguridad, no una librería utilitaria de las cuatro anteriores. Facilita autenticación, permisos y protección de contraseñas. Un hash BCrypt no es lo mismo que cifrar para luego descifrar.

En ServiClient: SecurityConfig configura PasswordEncoder y restricciones por roles.

Dependencias y seguridad

Una dependencia externa debe gestionarse: versiones compatibles, revisión de vulnerabilidades, actualizaciones y evitar componentes innecesarios. Las librerías aportan productividad, pero también hay que mantenerlas.

En ServiClient: Las dependencias se declaran en pom.xml y Maven gestiona su incorporación al proyecto.

Idea para explicarlo en voz alta: “No elegimos estas librerías solo para cumplir la consigna: Guava valida el registro de empresas; POI exporta Excel; Commons simplifica texto; Logback registra eventos; Spring Security controla acceso.”
Precaución para la sustentación: La presencia de commons-lang3 en pom.xml no demuestra que se use en dev. La evidencia verificada de StringUtils está en la rama feature/portal-usuario. Comprueba la rama antes de presentar.

Eje 3 · Control de versiones

Git y GitHub, sin confundirse

Git registra versiones del código; GitHub permite alojar el repositorio remoto y colaborar. Lo más convincente es enseñar las ramas y el historial real, no ejecutar un push de improviso.

Entiende la teoría antes de mostrar la implementación

Teoría: Git y GitHub desde cero

Git es el sistema de control de versiones que funciona con un repositorio local; GitHub aloja una copia remota y permite colaboración, revisión e integración de cambios.

Repositorio, commit y rama

Repositorio: archivos + historial. Commit: un registro de cambios con identificador y mensaje. Rama: una línea de trabajo donde se pueden realizar modificaciones sin afectar directamente otra rama.

En ServiClient: main es la rama principal; dev integra avances; feature/portal-usuario concentra trabajo sobre el portal.

Local y remoto

Local: proyecto en tu equipo. Remoto: repositorio alojado en GitHub. Los cambios pueden existir en una rama local aunque todavía no hayan sido enviados al remoto.

En ServiClient: En este proyecto se usa el remoto origin; git branch -a muestra ramas locales y de seguimiento remoto.

Traer cambios y enviarlos

git fetch actualiza las referencias remotas sin fusionar archivos; git pull recupera e integra cambios en la rama actual; git push publica commits en el remoto.

En ServiClient: Antes de enseñar ramas, puedes ejecutar git fetch origin y después mostrar git branch -a; evita fusionar cambios durante la exposición.

Preparar y guardar el trabajo

git status muestra el estado; git add selecciona cambios; git commit -m los registra localmente. Un commit no significa necesariamente que ya se subió a GitHub.

En ServiClient: Se pueden mostrar los commits con git log --oneline -5 y luego el historial de GitHub.

Idea para explicarlo en voz alta: “Git registra el historial y GitHub lo comparte. Trabajamos por ramas, guardamos avances con commits y los publicamos para que el equipo pueda integrarlos y revisar cambios.”
Precaución para la sustentación: Los porcentajes de lenguajes que muestra GitHub (Java, HTML, etc.) no indican porcentaje de funcionalidades completadas. No hagas un commit, merge ni push solo para la demostración.

El flujo del equipo

feature/...→Commits→GitHub remoto→Integración en dev→main (versión principal)

Ramas verificadas en el repositorio: main, dev, feature/portal-usuario, librerias-java y soledad. No es obligatorio mostrar todas: explica main, dev y feature.

Mostrar el sistema sin repetir toda la arquitectura

Los primeros ponentes ya explicaron el código. El último debe unir todo con un recorrido funcional de aproximadamente un minuto: lo que antes se vio en las clases, ahora se ve funcionando.

Entiende la teoría antes de mostrar la implementación

Teoría para cerrar: demostrar una función es conectar pantalla y código

La última persona no tiene que volver a explicar MVC, SOLID y todas las librerías. Su objetivo es demostrar un recorrido real y explicar en una frase cómo se relaciona con lo que ya presentaron.

Recorrido 1 · Inicio de sesión

Una cuenta autenticada accede a funciones permitidas por su rol. La demostración no necesita mostrar contraseñas ni crear usuarios nuevos.

En ServiClient: Mostrar la pantalla de ingreso con una cuenta de prueba ya preparada.

Recorrido 2 · Clientes

Una lista filtrada refleja el flujo: petición → controlador → servicio → repositorio → vista. Esto muestra MVC y DAO funcionando juntos.

En ServiClient: Abrir clientes y, si está disponible, utilizar búsqueda o consultar un cliente.

Recorrido 3 · Tickets

El Helpdesk registra incidencias con estados, prioridades y asignaciones. Aquí pueden observarse reglas de negocio y registros de actividad.

En ServiClient: Abrir un ticket existente y mostrar su información; no es obligatorio editar registros en vivo.

Cierre de equipo

El mensaje final une los tres ejes: estructura del código, librerías implementadas y control de versiones. La demostración prueba una función visible, no garantiza que todo el proyecto esté terminado.

En ServiClient: Cerrar indicando qué se ha implementado y qué sigue en revisión.

Idea para explicarlo en voz alta: “Lo que explicamos en el código ahora se observa en una funcionalidad real: el usuario ingresa, consulta clientes y revisa tickets. Estos módulos utilizan las capas y herramientas mostradas anteriormente.”

Guion visual sugerido: cliente → ticket

  1. Login de una cuenta de demostraciónDi: “Aquí vemos el inicio de sesión protegido por Spring Security”. Evita mostrar credenciales.
  2. Panel y lista de clientesDi: “Estas pantallas se generan con Thymeleaf y los datos se obtienen desde los servicios y repositorios”.
  3. Consultar o buscar un clienteDi: “Esta búsqueda usa el controlador, el servicio y una consulta del repositorio filtrada por empresa”.
  4. Ir a tickets y abrir uno existenteDi: “El módulo Helpdesk permite gestionar incidencias y seguir su estado”. Si es seguro y hay datos de prueba, puedes crear un ticket.
  5. Cerrar la exposiciónDi: “Así comprobamos que las capas, librerías, seguridad y control de versiones se aplican a una solución funcional”.
Plan B: si falla la aplicación, mantén preparadas 3 capturas reales (login, clientes y tickets) y explica el mismo recorrido; no intentes depurar MySQL durante la exposición.

Las 3 frases que conectan código con pantalla

“En el código mostramos el controlador; aquí vemos la pantalla a la que responde”.

“Los registros se consultan mediante servicios y repositorios, no desde la plantilla HTML”.

“Esta función aplica lo explicado: organización por capas, validación y seguridad”.

Evita afirmar que todos los módulos están completos; el Portal Usuario todavía tenía ajustes en la revisión de código.
